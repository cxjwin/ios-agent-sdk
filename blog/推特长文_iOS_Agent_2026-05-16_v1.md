# iOS 上做一个 agent

> 推特长文草稿 v1
> 2026-05-16
> 配套 repo: ios-agent-sdk

---

我老婆是前端工程师。有一天她问我"agent 到底是什么"，我没解释好。

回去我用 Claude Code 写了个 50 行的 JS demo 给她看,两次对话、10 几分钟搞定。两个工具,获取当前时间和四则运算,LLM 用 MiniMax。她看完说: 哦,就是个会自己调函数的循环。后来她用我们公司内部的 agent 平台自己也搭了一个,完成了她自己的闭环。

然后我开始想,iOS 上有没有人这么做。

---

我去查了一下生态分布。

Web 前端那边: LangChain.js、Vercel AI SDK、Mastra、agno —— 一大堆开源 agent 框架。CLI 那边: Claude Code、Codex、Aider、Cline、Gemini CLI —— Anthropic 自己 2026 年初把 "Claude Code SDK" 改名成 "Claude Agent SDK",公开承认这套 harness 可以服务编码以外的场景。

iOS / Swift 这边: **几乎是空的**。

不是 iOS 不该做,是没人填。Apple 自己有 Claude iOS app,但那是 consumer 产品,不是给开发者的 agent 框架。

那就自己填。我想看看 iOS 上做 agent 这件事,到底有什么独特的地方。

---

## 起步比想象简单

我打开 Claude Code,告诉它: "我想做一个 iOS agent SDK,参考 Anthropic 的 building-effective-agents。"

它列了个计划: Agent 主类、ToolProtocol、LLMClient 抽象、消息循环、工具调度。我跟它聊了几轮把架构敲定。我说"我只有 GLM 和 MiniMax 的 API",它自动把 LLMClient 抽象成 protocol,没把 API 写死 —— 这一步它的工程品味比我预期的好。

第一版 demo 几个小时跑通。不是因为我变强了,是 2026 年的工具链已经完全不同。模型对 Swift / iOS framework 的训练数据够好了,agent harness 范式被 Anthropic 抽象清楚了,tool use 协议已经在主流 provider 之间收敛了。

但 Claude Code 替不了我做的事 —— **决定方向**。哪些系统 API 值得做成 tool、harness 的终止条件怎么设计、并发策略怎么定、用户撤销 HealthKit 权限后 agent 怎么降级。这些是我作为 iOS 工程师积累下来的判断力,AI 没法替代。

**LLM 辅助开发 + 领域判断力 = 1+1 远大于 2**。niche 平台的开发者在 AI 时代的优势反而被放大了。

---

## 5 天后做出了什么

从 0 到能用的 SDK + demo 状态:

- 17 个原生工具,覆盖 HealthKit / EventKit / CoreLocation / Contacts / MapKit / 天气 / Reminders / Shortcuts / AVFoundation
- ~550 行 harness (Agent loop + AgentEvent 流式事件 + ToolExecutor)
- 三个 provider 跑通 (GLM / MiniMax-Anthropic 协议 / MiniMax-OpenAI 协议)
- 一句 prompt 跑通"晨间播报": 3 轮 LLM、并发 6 工具、6 秒出结果

demo 里我做了一件意外有用的事 —— **把 agent 的内部事件流式吐到屏幕上**。turn 开始、LLM 请求、工具调用、工具完成、最终回答,每个事件带时间戳实时滚动。原本是给最终用户的进度反馈,结果意外成了我自己的 profiler。

我给老婆看了这个 iOS 版的晨间播报 demo。她看完说: "哦,它就是一个会自己查东西的助理。"

那一刻我意识到, **agent 不是工程概念,是 UX 概念**。while 循环你跟非工程师讲不通,但屏幕上滚动的"在查睡眠… 在查日程… 在查天气…"她一秒就懂。

---

## 为什么是 iOS

按 Anthropic 的 4 组件框架 (model / harness / tools / environment),**iOS agent 跟其他 agent 的差异主要在 environment 层**。同一个 model、同一个 harness、放到不同 environment 里就是不同物种。

iOS 这个 environment 独占的资产有几样:

**1. 用户数据是一座金矿,而且跟隐私强绑定**

睡眠、心率、步数、日程、位置、通讯录、相册 —— 这些数据本来就只在你的 iPhone 上。浏览器 agent 拿不到(数据不在云端),CLI agent 拿不到(没人会把这些数据导出到 ~/)。**这是别的 environment 复制不了的护城河**。

而且 iOS 的沙箱 + per-data-type 权限模型是 Apple 花 15 年磨出来的:每个工具首次调用都触发系统级权限弹窗,用户能在设置里随时撤销。我做 SDK 是在继承这套机制,不是自己造。对比 CLI agent 一个 `--dangerously-skip-permissions` 就能 `rm -rf ~/` —— iOS agent 是**唯一一个能拿深度个人数据 + 用户每一类都明确点过"允许"**的物种。

**2. 苹果生态对 agent 工具化天然友好**

2026 年初 OpenClaw 在 Mac 上爆红 —— 那个项目的核心开发者之前也是 iOS 出身,靠 AppleScript + 大量 CLI 把 macOS 系统能力打包成 agent 工具。这个路径在 iOS 上对称存在: HealthKit、EventKit、CoreLocation 这些 API 设计得足够好,**可以直接桥接成 tool,不需要中间适配层**。

**3. App Intents 是 Apple 留下的"agent 基础设施"**

Apple Intelligence 这两年没跑通,但配套推的 App Intents framework 没废 —— 各 app 已经按 Apple 要求把核心能力封装好了。我可以把自家 app 的业务能力封装成 AppIntent,在同一进程里直接给 agent 调用。**Apple Intelligence 跑不通的红利,留给了第三方 iOS agent**。

---

## iOS 也有自己的局限,得诚实说

read_file / write_file / web_search 这些在 CLI agent 里开箱即用,iOS 上没有官方默认实现。但 iOS 有自己的对应 API (沙箱内文件系统可读写)、搜索可以接 Google Search SDK —— 只是需要额外开发。

反过来看 CLI agent 想拿 HealthKit / EventKit 的数据反而更难。**每个 environment 都有自己的能力盲区,不是绝对的优劣,是互补**。

---

## 当前还没做、roadmap 上的事

按 4 组件框架归类:

- **tools 层**: MCP client (接通外部工具市场)、App Intents 桥接 (复用自家 app 能力)
- **harness 层**: Agent Skills 支持 (按需加载专业知识)、Persistent session、并发工具执行
- **model 层**: Foundation Models 路由 (iOS 26+ 端侧推理)
- **environment 层**: 主端 app 集成(这是未来的事)

---

## 这五天最大的收获不是代码

是这个工作流:

模糊概念 → 让 AI 生成最简 demo → 直观理解 → 触发联想 → 跟 AI 沟通对比方案 → 联系自己的诉求 → 往业务和未来挖。

**AI 时代你只要有一个模糊的概念,就可以往下深挖**。正负反馈极快,几小时能验证一个想法,几天能把一个概念体系化地梳理下来。

我老婆问我 agent 是什么的时候,我自己其实也只是粗浅的概念。是这五天的实践让我真正搞清楚: agent 是 while 循环 + 工具 + 在哪个 environment 跑, **iOS 是其中最被低估的那个 environment**。
